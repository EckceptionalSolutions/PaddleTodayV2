## Initial cutover and routine publishing

`cloudflare-frontend-cutover.yml` takes an exact source SHA already published on the canary. It repeats the canary checks, builds production assets without the canary indexing exclusion, and snapshots every DNS record and current Worker domain before changing routing. The initial state must match the existing Azure CNAMEs: apex proxied, www DNS-only, both targeting `jolly-river-0d74c2110.1.azurestaticapps.net`.

Production uses `paddletoday-frontend` for apex static assets and the fixed-origin API proxy. The live Azure baseline also redirects every www path to the apex with HTTP 301, preserving queries; `paddletoday-www-redirect` preserves this behavior without fetching Azure or invoking the main asset Worker. Apex static requests continue bypassing Worker invocations. The sampled total zone traffic of 6,514 requests/day remains below the shared 100,000/day Free Worker allowance even if every existing request invoked a Worker; this is a sample, not a forecast.

Each production hostname has its own Custom Domain and an explicit expected Worker owner. Although Wrangler 4.158.0 sends a DNS override option, the actual API rejected the existing CNAME with error 100117 (run 42078482663); that attempt left DNS unchanged. The corrected sequence saves a separate recovery artifact, uploads both Workers privately, verifies their exact source tags and route-write permission, then releases only the unchanged, backed-up CNAME ID immediately before attaching each hostname. Same-name MX/TXT records and all other DNS records must retain their fingerprint. Deployment controls are checked out from the trusted workflow revision independently of the pinned frontend candidate.

GitHub-hosted runners receive the existing Cloudflare bot challenge on the public site and API (read-only run 42080612693). The workflow preserves that protection: it checks HTTP behavior and real authentication on the canary, then verifies production domain ownership and 100-percent active, source-tagged Worker versions through the authenticated Cloudflare API. Those checks do not establish public HTTP success. Public release markers, HTTP/search behavior, www redirects, TLS and mobile association files must additionally pass from the existing allowed workspace client before retirement. The workflow attempts Azure restoration after an initial routing or verification failure. Its independent Azure-origin check accepts the existing canonical 301 without following it through the public CDN.

The existing frontend workflow retains Azure by default. After successful cutover and public checks, set repository variable `FRONTEND_HOSTING_PROVIDER=cloudflare`. Routine releases continue publishing deduplicated Blob assets, verify the compiled package and authentication on the canary, restore production indexing headers, then deploy and verify source-tagged Workers. A preflight ownership guard prevents a routine deploy from claiming domains that were removed or reassigned. No hosting or DNS change occurs merely by merging this preparation.

Workers retains incoming query strings on static redirects. The search verifier ignores only its own cache-busting probe parameter when comparing destinations; canonical paths, fragments, and all other query parameters remain checked. Original page-level robots metadata remains intact, including deliberately nonindexable detail pages.

## Recovery and retirement requirements

The safe recreation configuration, exact version IDs and source revisions are retained in the [rollout evidence](frontend-hosting-rollout-2026-11-05.json). The existing API stays on B1.

The historical Azure recovery operation applies only while the original Azure resource exists: `operation=rollback-azure`, with `backup_run_id` from the initial cutover, checks the backup identity and Azure origin before changing routing. The original resource is now retired, so routine recovery uses Worker versions. An Azure recreation would require a fresh deployment, linked-backend configuration, and review of its new generated hostname before changing DNS; the saved configuration does not guarantee reclamation of the old hostname.

For recovery after Azure retirement, dispatch `operation=rollback-worker`, both verified Worker version UUIDs (`worker_version_id` and `www_worker_version_id`), and their matching `source_revision`. The operation checks production ownership, rolls back both Workers and associated assets, and verifies active source tags through the Cloudflare API. Repeat the public HTTP checks from an allowed client. Both rollback and restoration were exercised successfully before retirement.
